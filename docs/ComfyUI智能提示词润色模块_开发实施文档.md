# ComfyUI 桌面端「提示词智能润色」模块开发实施文档

> 给 Cursor / AI 编程助手直接执行的开发规格。适用于已经实现远程调用 ComfyUI 文生图 API 的桌面软件。
>
> 配套文件：`ComfyUI本地提示词润色库_v1.json`。请将两者放入项目工作区。

## 0. 本次任务目标

在现有生图客户端中增加提示词润色流程，保留现有生图 API、任务队列和结果展示逻辑，不重写已经运行稳定的后端。

用户流程必须为：

1. 输入原始描述词。
2. 选择模式：**本地润色库（离线）** 或 **AI 智能润色**。
3. 点击「润色提示词」。
4. 显示润色结果，用户可以直接编辑。
5. 清楚显示本次补充内容、保留的关键要求及可能的推断/冲突。
6. 用户明确点击「使用此提示词生图」后，才提交现有 ComfyUI 生图 API。
7. 保留原始文本，支持恢复原文、复制结果、重新润色。

**禁止**在润色完成后静默自动生图；禁止覆盖用户原始输入；禁止把未经确认的 AI 结果发送给生图 API。

## 1. 核心产品原则

### 1.1 保留用户意图优先于“写得更丰富”

润色要提升表达清晰度，不是替用户创作另一个画面。必须优先锁定：

- 主体、主体数量、身份/物种；
- 颜色、尺寸、材质、服装、部件；
- 动作、姿势、物体之间的关系；
- 地点、年代、天气、时间；
- 风格、镜头、构图、视角；
- 指定文字、品牌、符号和版式；
- 明确的排除要求，例如「不要人物」「只要一个物体」。

不允许在本地或 AI 润色时擅自添加第二个主体、改变颜色、把白天改夜晚、把全身图改特写、把写实改动漫，或给用户的场景额外添加天气、建筑、武器、人物、文字等。

### 1.2 诚实的质量边界

**任何提示词词库或语言模型都不能保证生成图像绝对不变形、没有常识错误。** 提示词只能降低一部分风险。对于精准结构、固定姿态、多视图一致性、正确文字、精确手部动作等要求，必要时还要用参考图、ControlNet/姿态控制、IP-Adapter、局部重绘、后期排版等工作流能力。

UI 不得出现「保证不变形」「百分之百准确」等承诺。建议使用「减少常见结构问题」「提升提示词清晰度」等描述。

### 1.3 本地模式真的离线

选择「本地润色库」时不得发起任何网络请求，不得访问 AI 服务，不得尝试云端兜底。应在开发者工具/网络测试中可以验证其不产生外部请求。

本地模式采用「关键词检测 + 分类规则 + 模型档案 + 双语片段 + 去重/长度控制 + 原意保留检查」，不要把它假装成理解能力与 LLM 一样的模型。

## 2. 交付内容

请实现以下内容，不要只给设计稿或伪代码：

- 现有桌面客户端内可操作的提示词润色 UI；
- 本地规则润色引擎；
- 加载和校验 `ComfyUI本地提示词润色库_v1.json` 的逻辑；
- 可配置的 AI 润色 Provider；
- AI 输出结构校验和失败处理；
- 原始文本/结果文本的编辑、差异说明和手动确认；
- 生图提交前的参数映射；
- 自动化单元测试、边界测试和手动验收步骤；
- README 中的配置说明。

请先阅读现有项目结构并复用现有组件、主题、请求封装、历史记录、密钥保存和生图接口。不要盲目创建第二套 API client 或更改已运行的接口字段。

## 3. 推荐 UI 方案

在现有生图页面的「正向提示词」输入区域附近增加一个「智能润色」面板，避免把主要生图流程拆到复杂的新页面。

### 3.1 面板布局

**顶部：模式开关**

- 单选/分段切换：「本地润色库（离线）」与「AI 智能润色」。
- 默认选择本地模式，或沿用用户最近一次选择；第一次使用必须清楚说明模式差异。
- 本地模式显示「离线，不会调用网络 AI」提示。
- AI 模式显示当前 Provider/模型配置状态；未配置时显示「前往设置配置」，不要伪装为已可用。

**中部：输入与结果**

- 左侧/上方：原始描述词。保留当前用户输入，润色过程不得修改它。
- 右侧/下方：润色后的正向提示词，可直接编辑。
- 若现有工作流使用负面提示词，保留并展示负面提示词编辑区；不能假设所有模型都使用负面提示词。
- 支持中英提示词输出：跟随原文、中文、英文。默认「跟随原文」；不得无提示地将语言切换成英文。
- 结果区可选「精简」「标准」「详细」三档。默认标准。详细模式也不可无差别堆砌词汇。

**结果解释区**

至少显示：

- 「本次补充」：新增的材质、空间、光照、构图等元素；
- 「已保留」：从原文识别到的主要要求；
- 「需要确认」：检测到的冲突、含糊或者可能属于 AI 推断的内容；
- 可折叠查看润色前后的差异。

解释区的内容必须基于真实结果，不可以固定写死「已完整保留所有要求」。本地引擎只能把已检测到的约束标为已保留，不得声称完成了深度语义理解。

**底部操作**

- 「润色提示词」
- 「恢复原文」
- 「复制结果」
- 「使用此提示词生图」

「使用此提示词生图」按钮只有在结果存在且没有未处理的严重冲突时可用；如检测到警告，可以允许用户明确确认后继续。点击后沿用现有生图任务链路，并把最终编辑后的提示词发送给 ComfyUI API。

### 3.2 视觉要求

- 延续现有桌面端的主题、字体、间距和按钮风格，不要另起一套不一致的设计语言。
- 原文和结果应有明确层级，但避免彩色卡片堆满页面。
- loading、空结果、复制成功、AI 超时、API 配置缺失、网络断开、JSON 解析失败、本地库缺失、原文为空等状态必须真实可见。
- 润色过程中禁用重复提交按钮，完成后恢复。
- 长文本输入区支持滚动、自动调整高度或合理的固定高度；布局不能在小窗口中溢出。
- 添加键盘可访问性：Tab 导航、清晰焦点样式、按钮语义正确。

## 4. 本地润色引擎实现规则

### 4.1 加载词库

加载配套文件 `ComfyUI本地提示词润色库_v1.json`，检查：

- JSON 格式有效；
- `schema_version` 受当前引擎支持；
- 分类 ID 唯一；
- 每个分类存在 `keywords_zh`、`keywords_en` 和至少一个语言的补充片段；
- 模型档案存在 `unknown` 兜底项。

库文件应作为可替换的应用资源，不能在代码里又复制一份硬编码词库。找不到词库时显示明确错误，并允许用户原样生图；不要导致整个客户端不可启动。

### 4.2 推荐算法

本地模式不是 LLM。使用可测试、确定性的规则流水线：

1. 读取原始正向提示词、负向提示词、用户选定的风格/输出语言/模型档案。
2. 保留原文原样副本，用于恢复和差异对比。
3. 做低风险预处理：规范化多余空格、分隔符；不要改写用户正文。
4. 从原文检测明确约束：数字与数量词、颜色、主体名词、动作词、否定语句、方向/视图、风格词等。检测结果记为 `lockedConstraints`，作为后续不可覆盖的数据。
5. 检测语义类别时，必须考虑否定上下文。例如「不要猫」不能因包含「猫」触发建议添加猫；「不要人物，只画汽车」中的人物是排除对象。
6. 根据词库关键短语命中数、短语优先级、分类优先级计算得分，选最多 3 个类别。不得因单字偶然出现就应用长段模板。
7. 对每个类别最多选择 3 个补充片段；每条片段应与原文相关，且不能与 `lockedConstraints` 冲突。
8. 最多添加 2 个通用质量片段，不要把所有「清晰、8K、最高质量、电影感、真实感」堆到每个提示词。
9. 依用户选择的模型档案生成正向文本。原则上主体与动作在前，其次是用户指定属性、空间关系、场景、风格和光线。
10. 对结果做去重、长度控制、冲突扫描和原文关键约束保留检查。
11. 返回结构化结果与解释；等待用户查看、编辑和确认。

如果检测到多个互斥元素，例如「白天夜景」「正视图低角度特写」「写实卡通」，不要悄悄替用户选一种。显示「可能存在冲突，请检查」并尽量保留原始措辞。

### 4.3 长度控制与去重

- 默认输出不超过原文约 2.5 倍；极短描述可以补充必要结构，但不能自动扩展成大段故事。
- 删除完全重复的片段和显然重复的质量词。
- 质量补充应短而具体，例如「光源方向一致」「建筑透视连贯」，不要只加无信息量的「masterpiece、best quality、8k、ultra detailed」。
- 不自动加相机型号、镜头焦段、天气、时间、烟雾、粒子、额外背景人物或道具。

### 4.4 负面提示词策略

- 保留用户原有负面提示词；本地润色不得自动覆盖它。
- 是否建议负面词由 `model_profiles` 与实际工作流决定。
- 如果工作流没有负面输入节点，不能擅自改工作流去强塞负面提示词。
- 对许多 FLUX 工作流，不应默认依赖传统负面提示词。优先在正向提示词里描述期望的视觉状态；必须服从用户真实 checkpoint 和 workflow 配置。
- 如要向负面提示词追加内容，只建议当前触发类别的少量词组，默认 4–8 个相关项上限，并让用户可编辑/撤销。

### 4.5 输出数据结构

本地引擎和 AI Provider 尽量使用同一数据结构：

```ts
export type PolishMode = 'local' | 'ai';
export type PromptLanguage = 'match_input' | 'zh' | 'en';
export type PolishDetail = 'concise' | 'standard' | 'detailed';

export interface PromptPolishResult {
  mode: PolishMode;
  originalPrompt: string;
  enhancedPrompt: string;
  originalNegativePrompt?: string;
  enhancedNegativePrompt?: string;
  addedDetails: string[];
  preservedConstraints: string[];
  assumptions: string[];
  conflicts: Array<{
    code: string;
    message: string;
    severity: 'info' | 'warning' | 'blocking';
  }>;
  matchedCategories: string[];
  modelProfile: string;
  outputLanguage: PromptLanguage;
  generatedAt: string;
}
```

AI Provider 如果返回了缺字段、错误类型、过长内容或不可解析 JSON，必须校验并提示错误。不要直接把模型原始回复塞进正向提示词。

## 5. AI 润色模式

### 5.1 Provider 抽象

设计统一接口，支持将来替换不同的 OpenAI-compatible 或其他语言模型服务。不要把某个供应商写死在 UI 组件中。

建议接口：

```ts
export interface PromptPolishProvider {
  polish(request: PromptPolishRequest): Promise<PromptPolishResult>;
}
```

设置项至少包括：

- API Base URL；
- API Key；
- 模型名称；
- 请求超时；
- 输出语言和详细程度；
- 测试连接按钮；
- 启用/禁用 AI 润色。

API Key 不得写入前端源码、普通日志或仓库配置。Electron 项目优先使用系统安全存储（如 Electron `safeStorage` 包装的主进程存储）或现有项目的安全凭据方案；不要把密钥经无保护的 IPC 暴露给渲染进程。

### 5.2 AI 系统提示词

将下面原则作为可版本化的 system prompt，不要只依赖用户提示词来限制模型：

```text
你是一个保守、精确的文生图提示词编辑器，不是自由创作代理。

任务：优化用户提供的图像描述，使画面主体、空间关系、材质、光照和构图更清楚。

硬性要求：
1. 原样保留用户的核心主体、数量、身份、颜色、动作、地点、年代、天气、服饰、配件、风格、镜头、视图、构图与指定文字。
2. 不能添加用户没有要求的新主体、人物、动物、道具、建筑、武器、标志或剧情事件。
3. 不能把用户未指定的风格、时间、天气、光效、相机镜头设定当成事实加入。
4. 可以补充与场景相关的空间关系、材质区分、自然透视、清晰的焦点和一致的光照；这些补充不能与原文冲突。
5. 用户给出明确的排除条件时必须遵守，例如“不要人物”“只要一个物体”。
6. 发现原文存在实质冲突时，不要私自决策；列入 conflicts/assumptions，尽可能保守地保留原意。
7. 根据请求中的目标模型档案调整表达；未知模型时采用清晰、适度的主体优先描述。
8. 不要无差别添加 masterpiece、best quality、8k 等空泛词。
9. 提示词优化不能保证图像绝对正确，不得声称保证无畸变。
10. 只返回符合约定 schema 的 JSON，不要附加 markdown 围栏或额外说明。
```

### 5.3 建议的 AI 请求参数

输入：原始正向提示词、原始负向提示词（可能为空）、目标模型档案、输出语言、详细程度、可选的用户选项。

必须要求 AI 返回：

- `enhanced_prompt`：最终可编辑提示词；
- `added_details`：新增描述点；
- `preserved_constraints`：明确保留的用户要求；
- `assumptions`：模型可能作出的推断；
- `conflicts`：潜在冲突；
- 可选的 `enhanced_negative_prompt`，但不能强制所有模型都输出。

将 `originalPrompt`、请求模式和时间戳由客户端自己填入，不要相信模型返回的这些元数据。

### 5.4 失败回退

- AI 超时、网络断开、认证失败、速率限制、模型输出非法 JSON：显示原因和重试入口。
- 默认不要悄悄切换成另一模式，以免用户误以为获得了 AI 结果。
- 可提供明确按钮「改用本地润色」，由用户主动切换。
- AI 返回内容为空时保留原文。
- AI 响应失败不应影响原有生图 API。

## 6. 与现有 ComfyUI 生图链路集成

1. 不重写现有生图请求模块。
2. 添加润色模块只生产 `PromptPolishResult`。
3. 用户修改 `enhancedPrompt` 后，最终生图参数必须读取编辑器当前值，而非最初 AI 返回值。
4. 如使用负面提示词，读取用户最终确认的负面提示词。
5. 提交前展示/保留用户现有的尺寸、步数、CFG、seed、模型和其他生图设置，不要因润色模块而重置参数。
6. 用户点击「使用此提示词生图」才进入已有的任务提交流程。
7. 日志只记录模式、模型档案、类别 ID、耗时和错误码；默认不要把完整私人提示词或 API Key 写入日志。
8. 如果目前生图 API 没有负面提示词、模型档案等字段，不要擅自扩展外部 API 合约。先使用已有字段，额外功能应单独评估兼容性。

## 9. 必须测试的用例

### 9.1 原意保留

- `一只黑色猫咪坐在红色沙发上`：不能多加猫、人物、雨天或赛博朋克；保留黑色、数量、沙发和动作。
- `不要人物，只画一辆蓝色跑车的侧视图`：不添加驾驶员；不将侧视图改成正面；不得因「人物」这个词误触发人像模板。
- `四视图的冰霜巨狼，用于3D建模`：不能改成三视图，不新增其他怪物，保留建模用途。
- `一个极简白色陶瓷咖啡杯，白底产品图`：不能擅自加品牌文字、咖啡馆、木桌或额外道具。
- `空旷的雪山夜景，不要人物`：不能加登山者或太阳升起。

### 9.2 本地模式离线

- mock 网络层并断言本地模式没有 HTTP、fetch、WebSocket 或 AI Provider 调用。
- 在未配置 AI Key 的情况下，本地模式仍可完成润色。

### 9.3 编辑与提交流程

- 润色后手动改写结果，再点生图；断言发给后端的是编辑后的文本。
- 点「恢复原文」后，结果区恢复最初输入。
- 点「复制结果」复制用户当前编辑后的文本。
- 润色失败不清空原文。
- 用户没点「使用此提示词生图」前，不允许提交生成任务。

### 9.4 模型档案与负面词

- FLUX 档案默认不自动拼接传统负面词，并把希望避免的状态转成正向要求。
- SDXL/SD1.5 只有在现有工作流支持负面输入时才允许展示对应编辑/建议；不得强制覆盖已有负面提示词。
- 未知模型用保守档案。

### 9.5 UI 和异常

## 12. 参考原则

- FLUX 提示词常见结构是主体 + 动作 + 风格 + 场景/上下文 + 光线/技术细节，并强调直接描述期望状态；具体应按实际 FLUX 版本与工作流确认。
- 不同图像模型的提示词和负面提示词支持存在差异，不能把同一组规则无差别应用于所有模型。
- 参考：Black Forest Labs 官方提示词指南（FLUX.2）：https://docs.bfl.org.cn/guides/prompting_guide_flux2
- 本地词库提供的是保守规则补充，必须通过目标 checkpoint 的固定 seed A/B 测试验证收益，不能仅凭提示词变长就认定画质更好。
