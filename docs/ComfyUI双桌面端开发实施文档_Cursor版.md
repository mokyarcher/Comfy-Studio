# ComfyUI 双桌面端产品开发实施文档（Cursor / AI 编程助手执行版）

> **项目目标：** 在现有“ComfyUI 本地文生图工作流 + FastAPI 封装 API + FRP 公网隧道”已经成功远程出图的基础上，开发两款精美、可靠、可打包安装的 Windows 桌面软件：
>
> 1. **Comfy Gateway（服务端控制台）**：安装在运行 ComfyUI 和现有 API 服务的 Windows 电脑上，用图形界面管理 ComfyUI 连通性、FastAPI 服务、FRP 客户端、工作流配置、API 密钥、运行日志和诊断。
> 2. **Comfy Studio（远程生图客户端）**：安装在需要调用 API 的电脑上，通过域名/HTTPS 调用远程 API，提供提示词编辑、参数设置、任务状态、生成结果画廊、历史记录、预设管理和图片导出等功能。
>
> 两款应用使用统一视觉语言，但必须是**两个独立桌面应用、两个独立启动入口、可分别打包安装**。不要把它们做成两个网页，也不要把它们合并成一个只能在服务端机器上运行的应用。

---

## 0. 给 Cursor 的执行要求（请优先阅读）

请先检查当前工作区和现有代码，再开始编写。**当前远程 API 已经可以正常生成图片，现有实现是基准资产，不是待重写的示例代码。**

必须遵守：

1. 先阅读现有项目目录、依赖文件、README、API 入口、工作流 JSON、配置文件、启动脚本和 FRP 配置；确认当前接口的真实请求体和响应体。不要根据本文件猜测实际字段。
2. 不要删除、覆盖或大规模重构现有 FastAPI / ComfyUI / FRP 代码。新桌面端放进独立目录，优先复用现有服务。
3. 保留现有已可用的 `POST /v1/images/generate` 和 `GET /health` 契约（若当前实际路由不同，以实测代码为准）。任何新增接口必须向后兼容，不能导致目前已经成功的调用方失效。
4. 所有按钮必须有真实行为。禁止只有静态页面、假数据、空按钮或“点击后显示成功”的演示功能。若某功能当前没有后端支持，要么实现完整闭环，要么明确标注为后续功能并禁用，不得伪造状态。
5. 必须真正完成本地开发启动、类型检查、构建和基本测试；遇到构建错误要继续修复，不要只输出代码片段或说明书。
6. 不允许将 API Key、FRP Token、密码写死在源代码中、日志中或示例配置中。不得将敏感配置提交到 Git。
7. 桌面端默认使用简体中文，时间、错误信息和状态文字要自然准确；英文只用于协议、专业字段或用户填写的提示词。
8. 对现有 API 行为存在不确定时，优先从源码、运行日志和真实请求响应确认；不要擅自改变 API 字段或虚构可用端点。
9. 不要自动修改云服务器上的配置，不要自动执行危险的删除操作，不要自动关闭用户已有的未知进程。涉及覆盖配置、结束外部进程、删除图片或重置数据时必须二次确认。
10. 项目开发完成后提供：新增/修改文件说明、开发启动命令、测试结果、安装包输出路径、首次配置步骤和已知限制。

建议执行顺序：**代码盘点 → 现有 API 契约固化 → 统一 UI 基础 → 服务端控制台 → 远程客户端 → 联调 → 打包 → 验收**。

# 第一部分：产品与技术架构

## 1. 产品定位

### 1.1 Comfy Gateway：服务端控制台

运行位置：安装在有 GPU、ComfyUI 和当前 FastAPI 服务的 Windows 电脑。

主要价值：让用户不再需要每次打开 PowerShell 手工启动多个服务；用一眼能看懂的状态面板启动/停止 API、FRP 客户端，检查 ComfyUI 是否在线、查看服务日志、测试公网地址并管理配置。

**它是现有服务的桌面管理与启动器，不是重新实现 ComfyUI。** ComfyUI 继续负责运行工作流，原 FastAPI 继续接收生图请求，FRP 继续做隧道转发。

### 1.2 Comfy Studio：远程生图客户端

运行位置：任意可访问服务端公开 HTTPS API 的 Windows 电脑；不要求安装 ComfyUI，也不要求有 NVIDIA GPU。

主要价值：用户只需填写 API 地址、密钥和提示词，便可远程生图。所有生成任务和图片都应显示真实状态，结果可以下载、查看、重用提示词和管理本地历史。

### 1.3 统一品牌

临时产品名可先使用：

- **Comfy Gateway** — 服务端管理端
- **Comfy Studio** — 远程生图端

名称、应用 ID、图标、版本号应集中配置，后续便于替换。不要在代码各处散落硬编码应用名。

## 2. 技术选型

统一使用以下技术，避免 AI 同时引入多套框架：

- **桌面容器：** Electron
- **前端：** React + TypeScript + Vite
- **样式：** Tailwind CSS + shadcn/ui（或同等质量、可访问的组件封装）
- **图标：** lucide-react
- **页面状态：** Zustand；请求缓存/轮询使用 TanStack Query
- **表单校验：** React Hook Form + Zod
- **动效：** CSS transitions 为主，必要时使用 Framer Motion；动效克制、支持减少动态效果
- **HTTP：** 统一封装 fetch/客户端层；超时、取消、错误解析要一致
- **桌面打包：** electron-builder，优先 Windows NSIS 安装包，并可额外提供 portable 版本
- **客户端本地记录：** 在 Electron 主进程中管理文件读写；记录元数据用 SQLite 或稳健的 JSON 元数据存储。若选择 SQLite，必须验证 Electron 原生模块在打包环境正常工作；不得只在开发模式能运行。
- **测试：** Vitest + React Testing Library；关键桌面流程增加 Playwright 或等效端到端测试；API 使用 mock server 做离线测试。

不要在 React Renderer 中直接使用 Node.js 文件系统、子进程、系统命令或任意 Electron IPC。所有系统操作必须经过 Main Process + 白名单 Preload API。

### 2.1 建议目录结构

先尊重现有仓库。建议将桌面端新增到 `desktop/`，不要强行移动当前 API 项目。可采用下列结构；如果仓库已有合适结构，可以调整，但必须保持边界清楚：

```text
├─ 当前已有的 FastAPI 服务、workflow_api.json、启动脚本等（保留原位）
├─ desktop/

│  │  ├─ src/main/              # Electron 主进程、服务进程管理
│  │  ├─ src/preload/           # 最小白名单 API
│  │  ├─ src/renderer/          # React UI
│  │  ├─ assets/                # 图标、应用资源
│  │  ├─ package.json
│  │  └─ electron-builder.yml
│  ├─ studio/                   # Comfy Studio 独立 Electron 项目
│  │  ├─ src/main/              # 本地存储、安全密钥、文件导出
│  │  ├─ src/preload/
│  │  ├─ src/renderer/
│  │  ├─ assets/
│  │  ├─ package.json
│  │  └─ electron-builder.yml
│  └─ shared/                   # 可复用设计 token、类型或组件（可选）
├─ docs/
└─ README.md

如果共享组件导致构建和类型配置复杂，可先在两项目内各自实现稳定版本，再抽公共包；不要为了“架构漂亮”让项目无法运行。
```

## 3. 与现有 API 的集成边界

### 3.1 首先确认当前真实 API 契约

从现有后端源码和实际测试确认：

- API 基础地址和健康检查路径。
- 生图提交路径、认证 Header 名称、请求 JSON 字段。
- 成功响应中图片是 Base64、文件 URL 还是其他格式。
- 是否有 task ID、任务状态接口、队列接口、错误响应格式。
- 超时、单次最大图片数量、最大分辨率、采样步数上限。
- FastAPI 服务由哪个 Python 环境/命令启动，工作目录在哪里。
- FRP 是通过哪个 `frpc.exe`、哪个 TOML 配置文件启动。

把确认后的契约整理到 `desktop/docs/api-contract.md`，包含经过脱敏的请求/响应示例。不要把真实 API Key 或 FRP Token 放入文档。

### 3.2 当前接口兼容模式

若现有 API 与先前约定一致，客户端至少兼容：

- `GET /health`
- `POST /v1/images/generate`
- 请求 Header：`X-API-Key: <key>`
- 请求体字段以当前后端真实实现为准，常见字段可能包括 `prompt`、`negative_prompt`、`width`、`height`、`steps`、`seed`。
- 旧版响应可能包含 `success`、`prompt_id`、`seed` 和 `images[]`，图片项可能包含 `filename`、`mime_type`、`data_base64`。

以上是兼容检查清单，不代表应覆盖现有实现。必须以仓库中当前代码为准。

### 3.3 同步/异步任务兼容策略

如果现有 API 是“请求一直等待直到图片生成完毕”的同步接口：

1. 客户端使用明确的长超时，并显示生成中状态和耗时。
2. UI 不得因 HTTP 请求未返回而冻结；请求需要在后台异步执行。
3. 设置本地排队能力，默认一次只向服务器发出一个生成请求，避免占满显卡或超出服务并发限制。
4. 网络中断时标记为“结果未知/连接中断”，不能轻率显示“生图失败”并自动重复提交，以免同一任务重复生成。
5. 不能承诺取消远程 GPU 任务，除非后端确实提供取消接口；可以提供“停止等待”并说明远端任务可能仍在运行。

可在不破坏现有契约的前提下，额外开发异步任务接口，例如提交任务返回 `task_id`、查询任务状态、获取结果。但只有在后端实际实现且通过测试后，客户端才启用异步模式。若新增，请补齐持久化、状态恢复、错误处理和兼容测试。不要让两款桌面端依赖假造的任务接口。

# 第二部分：统一视觉与交互规范

## 4. 视觉方向

关键词：**专业创作工具、深色工作台、精致、稳定、信息清晰、微玻璃质感**。可以有高级感，但不要把整个界面做成半透明玻璃或大量霓虹灯，避免影响阅读。

### 4.1 颜色设计 token

以深色主题为默认主题，后续允许切换浅色主题。颜色集中定义为 CSS variables，不要散落魔法数值。

- 页面底色：深蓝灰/石墨色，不使用纯黑大面积铺底。
- 侧栏：比页面底色略深，边界使用低对比度描边。
- 主面板：略亮于底色，层级分明。
- 主强调色：电光紫或偏蓝的紫色，用于主要 CTA、选中项和关键数据。
- 辅助强调色：冷青色，只用于连接状态、模型状态或少数辅助信息。
- 成功：绿色；警告：琥珀色；错误：红色。状态不能只依赖颜色，还要配图标和文字。
- 文本：主要使用高对比浅灰白；辅助信息使用中灰，确保可读性。
- 边框：低对比细线；阴影柔和且层级统一。

建议基础变量：`--bg`、`--panel`、`--panel-elevated`、`--border`、`--text`、`--muted`、`--primary`、`--accent`、`--success`、`--warning`、`--danger`。颜色值由 Cursor 在实现时形成完整主题表，并保证对比度。

### 4.2 组件与布局规则

- 默认窗口：约 1400 × 900；最小尺寸不小于 1180 × 760。窄尺寸下主内容区可滚动，不允许控件互相覆盖。
- 左侧导航宽度约 220–240 px；顶部状态栏约 56–64 px。
- 页面内容使用统一网格和 8 px 间距体系；卡片圆角约 12–16 px。
- 标题有明确层级：页面标题、区域标题、说明文字、元信息，不要所有文字同字号。
- 主要动作使用一个清楚的主按钮；次要操作为中性按钮；危险操作使用危险色并二次确认。
- 按钮必须有 hover、pressed、disabled、loading 状态。
- 表格/日志应使用等宽字体显示时间、PID、HTTP 状态码和路径；普通文本不要大面积使用等宽字体。
- 图标统一使用 lucide-react；不混用 emoji 作为主要操作图标。
- 动效控制在轻微淡入、状态过渡、卡片展开范围；禁止拖慢交互的长动画。
- 每一页都要处理 Loading、Empty、Error、Success、Offline 状态；不能只做正常数据状态。
- 使用真实状态数据；示例数据只允许存在明确标记的 Preview/Demo 模式，不得混入正式首页。

### 4.3 桌面窗口体验

- 自定义标题栏可以实现，但必须保留清晰的最小化、最大化/还原、关闭按钮；Windows 窗口拖动区域要正确。
- 关闭服务管理软件时，如果 API 或 FRP 正在运行，不得默认直接结束。显示选择：`最小化到托盘`、`关闭窗口但保持服务运行`、`退出应用并停止由本应用启动的服务`。
- 只有用户明确同意，才关闭由本应用启动的子进程；绝不结束不属于本程序的进程。
- 托盘菜单可以包括：打开主界面、查看服务状态、启动/停止 API、启动/停止 FRP、退出。若当前状态无法确认，要显示“状态未知”，不能伪装已连接。
- 两款软件的应用图标、启动页、关于页面和版本号风格统一，但名称必须区分 Gateway 与 Studio。

## 5. Gateway 导航结构

左侧导航建议：

1. **运行总览**
2. **服务管理**
3. **工作流与 ComfyUI**
4. **公网入口**
5. **访问密钥**

7. **设置**

底部显示应用版本、服务端电脑标签、设置入口。顶部固定显示总状态：`本地服务`、`ComfyUI`、`FRP 隧道`、`公网 API`；使用文字标签 + 图标表达状态。

## 6. 页面 A：运行总览 Dashboard

### 布局

- 顶部：欢迎标题、当前配置环境名称、`启动全部` / `停止本应用启动的服务` 操作区。
- 主区域：四张服务状态卡：ComfyUI、FastAPI API、FRP 客户端、公网 API。
- 中部左侧：最近 1 小时的 API 请求与生图统计（如后端没有统计接口，可从本地受控日志统计；没有数据时明确展示“暂无数据”，不可伪造）。
- 中部右侧：服务健康检查摘要与上次检查时间。
- 底部：最近事件日志（最多 8–10 条）和快速操作。

### 每张服务卡需包含

- 状态：运行中 / 已停止 / 启动中 / 正在停止 / 异常 / 未配置 / 状态未知。
- 地址/端口或进程路径（按服务类型显示）。
- 启动、停止、重启、查看日志按钮（只显示合理操作）。
- 最后一次健康检查结果和时间。
- 有错误时给出短原因和“查看诊断”入口，不要只显示红点。

### 状态准则

- **ComfyUI 在线：** 对配置的 ComfyUI 基础地址请求其健康/系统状态接口，并以真实响应判断。请求失败不能直接断言程序没有运行，要区分“无法访问”和“进程未启动”。
- **FastAPI 在线：** 请求当前配置的 `/health`，以 HTTP 结果和响应正文综合判断。
- **FRP 运行中：** 只能表示本应用启动的 `frpc` 进程存在；若未验证公网链路，不能显示“公网已连通”。
- **公网 API 可用：** 使用配置的 HTTPS 公网地址做真实健康检查。连接失败时，提供 DNS/TLS/反代/隧道/API 的分层排查建议。

## 7. 页面 B：服务管理

### 服务操作

必须管理以下服务，但要允许用户分别启用/禁用其中一项：

1. ComfyUI（可选管理）：能检查状态；只有用户填写并确认有效的启动命令、工作目录和 Python 环境时，才允许从 UI 启动。默认先探测已运行的 ComfyUI，不能盲目重复启动。
2. FastAPI 生图服务：使用当前仓库真实启动方式。可配置 Python 可执行文件、虚拟环境、工作目录、启动模块/命令、监听地址、端口、额外环境变量。
3. FRP 客户端 `frpc`：可配置 `frpc.exe` 路径和 TOML 配置路径，通过子进程启动/停止，实时查看 stdout/stderr（敏感 Token 必须脱敏）。

### 安全运行规则

- 本地 FastAPI 默认绑定 `127.0.0.1`，通过 FRP 在本机回连；除非用户明确理解并确认安全风险，否则不应默认绑定 `0.0.0.0`。
- 启动前检查可执行文件/脚本是否存在、端口是否可用、工作目录是否正确、配置格式是否可读。
- 若端口已被占用，显示 PID/进程名（若系统允许获取）并提供说明。不得自动杀死进程。
- 仅管理由当前 Gateway 进程启动并记录的 PID/子进程树；重启应用后要谨慎恢复状态，必要时用端口探测和命令行信息识别，不能仅按 PID 盲目结束进程。
- Windows 停止进程树需有可靠实现（例如使用明确的子进程 PID 与受控任务终止方式），必须测试不会误杀其它程序。
- 所有操作都需有明确反馈：正在启动、健康检查中、已启动、启动失败、正在停止、停止超时。
- “启动全部”顺序建议：如需启动 ComfyUI，先启动/检查 ComfyUI → 等待 ComfyUI 可响应 → 启动 FastAPI → 检查 `/health` → 启动 FRP → 测试公网 API。任一关键环节失败，列出失败步骤，不要假报全成功。
- “停止全部”默认只停止由 Gateway 启动的 FRP 和 FastAPI；如要停止 ComfyUI 必须让用户选择，因为用户可能仍想在网页中使用 ComfyUI。

## 8. 页面 C：工作流与 ComfyUI

功能：

- 配置 ComfyUI Base URL（默认候选 `http://127.0.0.1:8188`，但以实际配置为准）。
- 显示连接测试、ComfyUI 版本/设备信息（仅展示接口真实返回且可可靠解析的字段）。
- 显示当前 API 使用的工作流 JSON 文件路径、文件存在状态、最近修改时间。
- 提供“打开文件所在目录”“选择工作流 JSON”“重新检查节点”功能。
- 只读展示关键节点映射：正向提示词、负向提示词、尺寸、采样器、输出节点等（如当前后端有节点映射配置）。
- 工作流配置变更前提示备份；绝不默认改写原 JSON。可生成备份副本。
- 若当前后端没有自动节点检测，不要显示“自动识别成功”；可以先提供“打开文件/检查文件有效性”及明确提示。
- 显示模型与工作流检查结果时，不尝试擅自下载几十 GB 的模型或自动安装未知自定义节点。

## 9. 页面 D：公网入口

### 配置字段

- 公网 HTTPS Base URL，例如 `https://img-api.example.com`。
- 健康检查路径，默认 `/health`。
- FRP 本地代理端口、远程端口、`frpc.exe` 路径、FRP TOML 路径。
- 展示当前配置的目标地址、最后一次连通性测试、延迟和详细错误。
- `复制 API 地址`、`测试公网连通性`、`打开公网健康检查`（只对合法的 HTTP/HTTPS URL 开放）。
- “公网调用示例”区可以显示经过脱敏的 curl/Python 示例，API Key 用 `<YOUR_API_KEY>` 占位。

### 不在本期默认做的事

- 不自动通过 SSH 修改云服务器上的 `frps`、Nginx、防火墙或 DNS。
- 不自动申请/续期证书。
- 不擅自开放公网端口。

可提供清晰的部署检查清单和复制配置模板，但远端系统变更留给用户确认与人工部署。

## 10. 页面 E：访问密钥

- 支持生成高强度随机 API Key、复制、轮换、禁用/重置（具体取决于当前 API 后端是否支持多密钥和热更新）。
- 必须检测现有后端到底如何读取 API Key：环境变量、`.env` 文件或配置文件；根据现有机制实现，不要做一个只改 UI 不改运行服务的假管理页。
- 对当前单密钥实现，提供“更新密钥并重启 API”流程：提示将影响已配置的客户端，展示确认步骤，成功后做一次鉴权测试。
- 密钥默认掩码显示；点击揭示或复制时需要用户主动操作。
- 本地优先使用 Electron `safeStorage`（Windows 上使用系统保护机制）保护敏感配置。不要把明文密钥放在 renderer、日志或导出的诊断包中。
- 如果当前运行环境无法可靠加密，必须提示用户，提供不保存或手动设置环境变量的选项；不可静默明文保存。
- 如果不支持多个调用者密钥，UI 要明确说明“当前版本为单密钥”，不要伪装已支持独立用户权限。

## 11. 页面 F：日志与诊断

- 合并展示由 Gateway 启动的 FastAPI 和 FRP 子进程日志，可分标签查看。
- 日志功能：自动滚动、暂停滚动、清空当前视图、搜索、级别筛选、复制选中行、导出日志。
- 保留时间戳、级别、来源服务；长日志要虚拟列表/限制缓冲，避免大量日志拖慢 UI。
- 对 API Key、FRP Token、Authorization、Cookie 等进行脱敏。所有异常都保留可供调试的非敏感上下文。
- 诊断报告内容：OS 版本、Gateway 版本、服务路径（必要时脱敏）、各服务健康检查、端口占用情况、最后若干条已脱敏日志。导出前显示包含内容与隐私提醒。
- 给出分层“问题定位”：ComfyUI、本地 API、FRP 进程、FRP 服务端、公网 DNS/TLS、Nginx 反代、API Key 鉴权。

## 12. 页面 G：设置

- 通用：主题（深色/浅色/跟随系统）、开机启动（默认关闭且需要用户授权）、最小化到托盘、关闭窗口行为、语言（首期简体中文）。
- 路径：Python、API 项目目录、ComfyUI、`frpc.exe`、FRP 配置、工作流 JSON。
- 网络：API 监听地址/端口、ComfyUI 地址、健康检查间隔、请求超时。
- 日志：最大保留大小/天数、是否保存文件日志。
- 配置支持导出/导入，但导出默认不包含任何密钥；导入配置时预览差异，不直接覆盖。

# 第四部分：Comfy Studio（远程文生图客户端）

## 13. Studio 导航结构

左侧导航建议：

1. **开始创作**
2. **任务队列**
3. **作品画廊**
4. **提示词库**
5. **API 连接**
6. **设置**

左下显示当前连接配置名称与状态。顶部状态条显示 API 可用/不可用、当前连接配置、当前待处理任务数量。

## 14. 页面 A：开始创作（主工作区）

这是 Studio 的核心页面，必须把注意力放在提示词和出图上，不能像管理后台一样全是小卡片。

### 建议桌面布局

- 主内容区左右两栏：左侧约 56–60% 为提示词与参数面板，右侧约 40–44% 为最近结果/当前生成预览。
- 顶部栏：页面标题、连接状态、当前 API Profile 下拉切换。
- 左栏从上到下：正向提示词、负向提示词、快速提示词工具、尺寸与基础参数、更多参数折叠区、主要生图按钮。
- 右栏：当前生成状态/进度（如后端没有真实进度，只显示“请求已发送/等待结果/处理响应”，不能伪造百分比），完成后显示较大的结果预览和操作按钮。
- 窗口变窄时变为纵向排列；提示词输入区域仍要有足够高度。

### 提示词编辑器

- 正向提示词输入框要显眼，支持多行、粘贴、清空、字数提示。
- 负向提示词放在独立可折叠区域，不要占据与正向提示词同等视觉重量。
- 提供插入模板、追加片语、替换文本、复制、清空、收藏当前提示词等实用动作。
- 支持本地保存常用提示词片段标签（如 `cinematic lighting`、`photorealistic`、`character turnaround`），每个片语可单击追加；不要默认把一长串无意义的质量词自动插入。
- 在发送前做基础校验：提示词非空、尺寸处于服务端允许范围、数字参数合法。前端校验不能取代后端校验。
- 不要随意裁剪用户的英文提示词、改变大小写或擅自翻译。

### 生图参数

首期只展示当前后端真正支持的字段；参数配置必须与服务端 API 契约一致：

- 宽度/高度：常用预设（512×512、768×768、1024×1024、横图、竖图）和自定义尺寸；如果服务端有限制，要从配置或契约体现，并在 UI 中约束。
- 宽高比快捷选项：1:1、3:2、2:3、16:9、9:16 等；选择比例应按规则更新尺寸，不得默默覆盖用户已输入值而不提示。
- Steps、Seed、CFG、Sampler、批量数量仅在当前 API 确实支持时启用。对未支持字段显示为禁用或隐藏，并给出简短原因；禁止发送后端不认识的字段并假称生效。
- Seed 提供“随机”与“固定”两种交互。若不输入 seed 由后端产生，应在结果区显示后端返回的实际 seed（如果后端确实返回）。
- 默认参数可以保存为本地预设：如“快速草图”“高质量”“角色概念图”“横版场景”，但预设只包含服务端支持的字段。
- 主要 CTA：`生成图片`；请求中显示 `正在提交…`，服务端受理后显示 `生成中…`，成功后显示 `生成完成`。
- 防止重复提交：请求过程中禁用同一任务的提交按钮，除非用户主动加入队列。

### 连接不可用时

- 如果 API 未配置或离线，保留编辑内容；显示“尚未连接 API / 无法连接”，提供“配置连接”和“重新测试”操作。
- 不要清空提示词，也不要把错误提示覆盖整个工作区。

## 15. 页面 B：任务队列

- 显示任务：等待中、正在请求、生成中/等待响应、成功、失败、连接中断/结果未知。
- 每项包含缩略图（若已有）、提示词摘要、尺寸、提交时间、耗时、seed（如可用）、状态和简明失败原因。
- 支持队列暂停/继续（只暂停本地尚未发送的任务）；删除等待中的本地任务；失败任务可由用户确认后重新提交。
- 同步 API 模式下要明确“远程处理进度不可用”，显示已等待时间/请求阶段，不能杜撰 43%、78% 等进度条。
- 应用关闭重启后恢复本地任务记录；对于关闭前正在执行而结果未知的任务，标记为“中断/状态未知”，不要自动重复生成。
- 默认客户端并发为 1；只有后端明确支持并发、并且用户设置允许时，才开放并发数设置。

## 16. 页面 C：作品画廊

- 以图片网格展示本地已保存的生图结果，支持网格/紧凑视图、缩略图预览和大图查看。
- 顶部工具：搜索提示词、日期筛选、尺寸筛选、收藏筛选、排序（最新/最早）。
- 每张图片卡片显示缩略图、提示词截断预览、尺寸、生成时间；点击可查看大图和完整参数。
- 图片详情侧栏：完整提示词、负向提示词、seed、steps、尺寸、API Profile、请求 ID（如有）、文件路径。
- 操作：保存到指定位置、在资源管理器中显示文件、复制提示词、重新使用参数生成、收藏/取消收藏、删除本地文件。
- 删除文件必须二次确认；默认只删除 Studio 复制到自己的作品库中的本地文件，不允许删除远程 ComfyUI 的文件或服务器文件。
- 接收 Base64 图片时先验证 MIME 类型和文件大小，再写入用户数据目录；文件名安全化，避免路径穿越和覆盖已有文件。
- 原图和缩略图分开管理；为大量图片生成缩略图，避免整个画廊一次性加载全分辨率原图。

## 17. 页面 D：提示词库

- 分为“我的模板”和“片语”两个分类。
- 模板字段：名称、分类、正向提示词、负向提示词、可选参数预设、标签、创建时间、最后使用时间。
- 分类示例：人物、怪物/生物、场景、科幻、暗黑奇幻、产品图、通用摄影；用户可自行新增分类。
- 支持新增、编辑、复制、收藏、搜索、标签筛选、导入/导出 JSON。
- 导入前校验 JSON 格式并展示变更预览；不允许直接执行导入文件中的脚本或 HTML。
- 可以提供少量高质量英文模板作为初始内容，但要允许用户删除/编辑；不要在每次运行时自动追加预设内容。

## 18. 页面 E：API 连接

### 多配置 Profile

支持保存多条连接配置，例如“家用 GPU”“备用服务器”“测试环境”。每个 Profile 字段：

- 显示名称。
- API Base URL，例如 `https://img-api.example.com`。
- API Key。
- 生图路由（默认来自当前 API 契约，普通用户不应随意改动）。
- 健康检查路径（默认 `/health`）。
- 请求超时秒数。
- 上次测试时间、结果和延迟。
- 是否为当前默认配置。

### 操作

- 新建、编辑、复制配置、设为默认、删除配置。
- `测试连接`：请求健康检查端点；根据当前后端的鉴权设计，如果健康检查无需 Key，则再用“鉴权验证”或可选的轻量 API 验证方式确认密钥。没有鉴权验证路由时不要伪造鉴权已通过。
- `保存并连接`：先校验 URL 格式和协议。
- 对公网地址优先要求 HTTPS。若 URL 为公网 HTTP，显示高优先级安全警告并要求显式确认；本机 `localhost`/`127.0.0.1` 的 HTTP 开发地址可正常使用。
- API Key 使用 Electron `safeStorage` 存储；配置列表只显示掩码。复制密钥需要用户点击。
- 禁止将 API Key 放到 URL query、日志、崩溃报告、统计事件或图片元数据中。

## 19. 页面 F：设置

- 主题：深色/浅色/跟随系统。
- 默认保存目录、缩略图质量、历史记录保留策略。
- 默认生图尺寸、默认负向提示词、默认 Steps（仅 API 支持时）。
- 默认 API Profile、请求超时、任务队列策略。
- 启动行为：启动时打开上次页面；默认不开机自启，用户可主动启用。
- 隐私：清理本地历史元数据、清理缓存缩略图、删除本地作品文件（危险操作须二次确认）。
- 关于：版本、构建信息、许可证/第三方依赖说明、打开日志目录。

# 第五部分：本地配置、进程、存储与安全

## 20. 配置存储约定

### Gateway

非敏感配置保存到应用 userData 目录中的版本化配置文件；敏感密钥使用 `safeStorage` 加密后保存，或使用可靠的系统密钥存储。不要把 `.env`、FRP Token、API Key 打包进安装包。

### Studio

连接 Profile 元数据保存在应用 userData 中，API Key 加密保存；生图图片放在用户数据目录下的 `gallery/` 或用户选择的输出目录；提示词历史只记录必要信息。

### 路径兼容

- 正确处理 Windows 路径中的空格、中文字符和反斜杠。
- 子进程启动使用参数数组和 `cwd`，不要通过不安全的 shell 拼接用户输入。
- 记录配置文件版本；升级时迁移旧版本配置，迁移失败时先备份旧文件再提示用户。
- 配置导入/导出默认移除密钥、Token 和任何凭据。

## 21. Electron 安全要求（必须实现）

- `contextIsolation: true`。
- `nodeIntegration: false`。
- Renderer 启用 sandbox；不要为图省事关闭安全选项。
- Preload 只暴露明确、最小的函数，例如 `gateway.startApi()`、`gateway.stopApi()`、`gateway.getStatus()`、`studio.saveImage()`，不允许暴露原始 `ipcRenderer`、任意文件读写或任意命令执行。
- 每个 IPC handler 都校验调用来源和参数格式；参数用 Zod 或等价方式校验。
- 不加载未知远程网页作为应用主体；页面资源全部随应用打包。
- 设置严格 Content Security Policy；禁止不必要的窗口跳转和新窗口创建。
- 对外部链接只允许经过校验的 HTTPS/HTTP 文档链接，并在主进程中安全打开；绝不能把用户提示词、服务器返回字符串直接作为任意 shell 命令执行。
- 生产环境不得打开 DevTools（允许通过显式开发选项开启）。
- 图片 MIME 类型和体积必须校验，不能相信服务端返回的文件名。
- 日志脱敏，API Key/FRP Token 不允许进入 console、IPC 错误原文、崩溃日志和诊断包。

参考 Electron 官方安全说明：
- https://www.electronjs.org/docs/latest/tutorial/security/
- https://www.electronjs.org/docs/latest/tutorial/context-isolation
- https://www.electronjs.org/docs/latest/tutorial/packaging

ComfyUI 服务 API 端点可参阅官方路由文档：
- https://github.com/Comfy-Org/docs/blob/main/zh/development/comfyui-server/comms_routes.mdx

## 22. Gateway 子进程管理实现要求

- 子进程管理写在 Electron Main Process 的独立 ServiceManager 模块中，不要在 React 组件中启动 shell 命令。
- 必须维护每个服务的生命周期状态机：`stopped → starting → running → stopping → stopped`，以及 `failed`、`unknown`。
- 记录本应用启动的 PID、启动时间、启动参数（密钥值必须脱敏）和退出码。
- 捕获 stdout/stderr；拆分超长行；限制内存日志缓冲；按文件轮转保存日志。
- 启动前检查路径、工作目录、命令和端口；错误信息应包含可执行的修复建议。
- API 的进程存活与 API 健康状态分开判断。
- FRP 进程存活与公网连通状态分开判断。
- 应用意外崩溃后，不要无条件自动杀掉已经启动的 API 或 FRP；启动时先侦测服务状态，并让用户选择接管/保持/停止。
- 进程退出或服务异常时发出事件更新 UI，不能只靠前端定时器猜状态。

## 23. 图片与历史存储

Studio 收到图片之后：

1. 解析和校验服务响应。
2. 校验 `mime_type` 是否属于允许的图片 MIME 类型（首期至少 PNG/JPEG/WebP，按后端实际能力决定）。
3. 对 Base64 数据设定大小上限，避免异常大响应耗尽内存。
4. 写入临时文件后原子重命名，避免程序中途退出生成半张文件。
5. 为文件生成唯一文件名；禁止直接把远端返回的文件名拼成完整写入路径。
6. 生成缩略图并保存元数据：日期、提示词、负向提示词、参数、来源 Profile、seed、任务 ID、文件路径。
7. 图片保存失败时保留错误信息，并允许用户重试保存；不要把任务标记为完全成功却丢失图片。

历史数据只保存元信息与本地文件路径，不要把 Base64 全部永久存入 JSON/数据库。

# 第六部分：网络错误、边界情况与可观测性

## 24. 错误处理标准

所有错误统一为用户可理解的中文，包括：

- API 地址格式错误。
- DNS 无法解析、连接超时、TLS 证书错误。
- 401/403 密钥错误或无权限。
- 404 API 路径不存在。
- 422 参数校验失败。
- 429 请求过多（若后端使用该状态码）。
- 500/502/503/504 服务错误、ComfyUI 无响应、等待超时。
- 服务端返回格式异常、图片 Base64 无效、磁盘空间不足、无法写入输出目录。
- Gateway 找不到 Python、FastAPI 依赖缺失、工作流文件缺失、FRP 路径无效、端口被占用。

错误页面或 Toast 至少包含：简短原因 + 下一步建议 + 可展开的技术详情（脱敏）。不要把完整堆栈直接当作普通用户的提示。

## 25. 诊断链路

Gateway 必须能单独测试以下每一层，而不是只有一个“全部正常”按钮：

1. ComfyUI 本地地址。
2. FastAPI 本地健康检查。
3. FRP 客户端路径和进程。
4. 云端 FRP 链路/公网 API 连通性。
5. HTTPS 证书和域名可访问性（以真实请求结果判断）。
6. API Key 鉴权（只有后端提供可靠方式时才显示通过）。
7. 一次可选的低成本生图测试（必须让用户主动点击，提示会实际使用本地 GPU）。

每个检查项记录检查时间、耗时、结果和脱敏错误，便于用户定位具体故障。

# 第七部分：构建、安装与升级

## 26. 开发与产物要求

两款应用分别提供脚本：

- `npm run dev`：启动开发版。
- `npm run typecheck`：TypeScript 检查。
- `npm run lint`：代码质量检查。
- `npm test`：单元测试。
- `npm run build`：生产前端构建。
- `npm run dist`：生成 Windows 安装包。

如果项目当前没有 lint 配置，可以使用 ESLint；必须让脚本真正可执行，不允许在 package.json 中留空脚本。

输出产物建议：

- `Comfy-Gateway-Setup-x.y.z.exe`
- `Comfy-Studio-Setup-x.y.z.exe`
- 可选 `Comfy-Gateway-Portable-x.y.z.exe` / 便携包（如果依赖和数据路径测试通过）
- 安装包输出目录写入 README，默认放在对应应用的 `release/` 或 `dist/` 目录。

安装、卸载和升级规则：

- 安装时不修改用户原有 ComfyUI 模型和工作流目录。
- 卸载时默认保留配置和作品历史，提供单独清理数据选项。
- 升级应用不能清理生成图片。
- 检查用户机器上路径和依赖，不应假定所有人都有同一盘符或固定安装路径。
- 不把 API Key、FRP Token、`.env`、真实 IP/域名等敏感配置写入默认安装包。
- 首次运行打开引导：Gateway 选择项目/程序路径与 ComfyUI 地址；Studio 填入 HTTPS API 地址和 API Key，并测试连接。

## 27. Python/FastAPI 服务的打包策略

第一阶段优先让 Gateway 管理当前已成功运行的 Python/FastAPI 服务：允许用户选择现有 Python 解释器、虚拟环境和项目目录，然后以受控方式启动现有服务。这可以最大限度避免破坏已正常工作的部署。

如果现有项目适合 PyInstaller，并且能验证打包后仍可找到配置、工作流和依赖，可再增加“自包含服务端组件”发行模式。但这属于可选增强，不要为追求一键安装而在第一版就强行搬迁/重写后端。

不论采用哪种模式，都必须做到：

- API 代码仍能独立从命令行运行，便于排障。
- 配置文件、工作流文件和日志路径可配置。
- 退出/重启逻辑可靠。
- 打包后在一台没有开发环境的干净 Windows 测试机上进行安装和启动测试；如果依赖外部 Python/ComfyUI，应在安装说明中明确写出。

## 30. 测试场景（至少覆盖）

2. API 域名错误/服务端关机。
3. API Key 错误。

12. Studio 在远程任务等待期间退出并重新启动。
13. 配置导入文件含无效 JSON 或恶意路径字段。
14. API Key 含特殊字符且经过保存/读取后仍能正常鉴权。
15. 安装版运行（不是只测试 `npm run dev`）。

# 第九部分：分阶段落地，避免一次性生成大量不稳定代码

## Phase 0：先做项目盘点

交付：

- 当前项目目录树与启动方式说明。
- 现有 API 路由、请求体、响应体、密钥来源、ComfyUI 地址、FRP 启动方式。
- `desktop/docs/api-contract.md`。
- 确认不需要更改的现有文件清单。

完成标准：明确当前链路可以工作的证据和测试方法。此阶段不重写后端。

## Phase 1：两个应用的视觉骨架

先构建两款独立应用的导航、设计 token、窗口布局、空状态/加载/错误状态、设置页面框架。随后立即接入真实数据，不要长期停留在 mock UI。

完成标准：两应用都能运行，页面层级明确，缩放合理，深浅主题可用（若首期来不及可先做好深色主题，但主题架构须可扩展）。

## Phase 2：实现 Gateway 的服务管理

优先完成 ComfyUI 检查、FastAPI 启动/停止、FRP 启动/停止、分层健康检查、日志、路径配置与密钥安全存储。

完成标准：在真实 Windows 机器上通过 UI 启动现有服务，然后在 Studio 或 curl 中验证 API 仍然能出图。

## Phase 3：实现 Studio 远程生图

完成连接 Profile、健康检查、真实生图、等待状态、图片保存、画廊、提示词历史/模板和设置。

完成标准：在另一台电脑上只安装 Studio，配置云端 HTTPS 地址与 API Key，即可完成一次远程生图并在本地看到结果。

## Phase 4：错误处理和打包

修复 lint/type/test/build 错误，完成安装版测试、配置迁移、日志脱敏、托盘行为和首次启动引导。

完成标准：生成两个独立安装包，并在 README 中写出输出位置与安装配置步骤。

## Phase 5：可选增强（不要阻塞第一版）

- 后端异步任务接口与可靠任务队列。
- 多用户/多 API Key、用量统计与配额（一期已落地：`/v1/admin/*` + Gateway「用户与监控」）。
- GPU/显存状态面板（需有可靠数据源）。
- 生图任务标签、批量生成、图片评分、收藏夹。
- 自包含 Python 服务打包。
- 自动更新和版本发布流程。
